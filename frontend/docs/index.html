OrbitDesk documentation

OrbitDesk workspaces contain dashboards, data connections, export schedules, members, and API credentials. Use this guide to check a product rule or troubleshoot a common failure. For a specific question, ask OrbitDesk for an answer grounded in the knowledge base.

API credentials

Workspace API credentials are for server-to-server integrations. Only an Owner or Admin can create or revoke one. An Analyst or Viewer cannot create a credential.

Create a credential

  1. Open Settings → Developer → API credentials as an Owner or Admin.
  2. Give the credential a display name and select only the scopes the integration needs.
  3. Store the secret securely when it is shown. OrbitDesk displays it only once.

A credential with dashboards:read cannot create or edit dashboards. If a secret is lost, revoke the credential and create a replacement; support cannot reveal it. If exposure is suspected, revoke it immediately.

Legacy personal tokens from Profile → Personal token were removed in version 4.0. Use a workspace credential instead.

Roles and permissions

Roles apply within a single workspace. They do not grant the same access in every workspace on an account.

Owner
Manages billing, ownership, deletion, members, workspace credentials, and all Admin and Analyst actions. Each workspace must have at least one Owner.
Admin
Manages members other than Owners, workspace settings, credentials, and connections. Cannot manage billing or transfer ownership.
Analyst
Creates and edits dashboards, runs manual exports, and creates schedules. Cannot create credentials or change workspace settings.
Viewer
Reads shared dashboards. Can download an export only when the dashboard owner enabled downloads. Cannot create schedules or credentials.

For permission_denied, check the role in the affected workspace and the attempted action. Credential creation needs an Owner or Admin—not necessarily an Owner.

Scheduled exports

Analysts, Admins, and Owners can schedule PDF or CSV exports. A run checks the schedule state, dashboard access, required refreshes, rendering, and then delivery. A schedule may be Active, Paused, Needs attention, or Running.

After a timezone change

Changing the workspace timezone does not update existing recurring schedules automatically. Open each affected schedule, review its next-run time, and select Save schedule. The Timezone update pending notice should disappear. This changes future runs; it does not recover an already missed export. One-time exports keep their absolute timestamp.

When an export is missing

  1. Check the schedule state and next-run time.
  2. Open Schedule → Run history and record the latest status and error code.
  3. Confirm the dashboard still exists and the schedule owner can open it.
  4. Check required connections and the delivery destination.
source_refresh_timeout
A required refresh exceeded 15 minutes. The export is not retried automatically.
destination_unverified
Delivery is blocked until the destination is verified.
owner_access_revoked
The schedule owner lost dashboard access.
render_failed
Rendering failed after the data checks. Escalate after two consecutive failures for the same dashboard.

After correcting the cause, use Run now. A manual run does not change the recurring schedule’s next-run time.

Connections and refreshes

Owners and Admins manage connections. Analysts can view non-secret settings and start a manual refresh when a connection allows it. A connection may be Active, Refreshing, Reauthorization required, Disabled, or Error.

Only one refresh can run for a connection at a time; a second request returns refresh_already_running. Exports wait up to 15 minutes for required refreshes. A later successful refresh does not change a run that already ended with source_refresh_timeout.

For reauthorization_required, an Owner or Admin must reconnect the source. For two repeated connector_internal_error failures, escalate with the connection ID, refresh job IDs, and timestamps.

Delivery destinations

Exports can go to email or a configured cloud-storage destination. The first export to a new external email domain needs Owner or Admin verification. Verification links expire after 24 hours and can be resent from Settings → Export destinations.

A schedule can include up to 20 email recipients. OrbitDesk records mail-server acceptance, not whether a recipient opened the message. If a message was accepted but cannot be found, check spam filtering and allow-list exports@orbitdesk.example.

An Owner or Admin must reconnect a storage destination in reauthorization_required state. The exact historical export file cannot be resent after its seven-day retention window; a new run may contain newer data.

Audit logs

Owners and Admins can open Settings → Audit log. Logs cover member and role changes, workspace settings, connection changes, export schedules, and credential creation or revocation. Analysts and Viewers cannot access this page.

Events are stored in UTC and displayed in the viewer’s selected locale. They remain available for 90 days. Changing the workspace timezone does not rewrite older events. When comparing an event with an export run, include the displayed timezone or convert both times to UTC.

Safe troubleshooting

Before escalating, collect the workspace ID, affected object ID, exact error code, timestamps with timezone, relevant run or refresh IDs, reproduction steps, and checks already tried.

Do not share passwords, API secrets, OAuth tokens, session cookies, payment-card numbers, or full exported datasets. Crop screenshots to remove unrelated customer information.

Escalate repeated documented failures, suspected credential exposure, ownership disputes, billing or legal requests, and reproducible errors not covered here. The support assistant can explain documented steps but cannot change an account, execute an export, issue a refund, or promise a resolution time.
